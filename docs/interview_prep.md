# ฝึกตอบคำถามสัมภาษณ์

แต่ละข้อมีประเด็นสำคัญกับตัวเลขจริงจากโปรเจกต์นี้ไว้ให้ เขียนคำตอบด้วยคำพูดของตัวเองลงในช่อง "คำตอบของฉัน" แล้วลองพูดออกเสียง ตอบข้อละไม่เกิน 1–2 นาที

---

## 1. เล่าภาพรวมของ pipeline นี้ให้ฟังหน่อย

**ประเด็น**
- ข้อมูล Online Retail 541,909 แถว แบ่งเป็นไฟล์รายวัน 305 ไฟล์
- validate ด้วย pandera → โหลดเข้า `raw` ส่วนแถวเสียไปที่ `audit.rejected_rows`
- dbt สร้าง star schema ใน `marts` → Metabase อ่านผ่าน role อ่านอย่างเดียว
- Airflow รันวันละ 1 run: setup → ingest → transform → notify
- CI รันเทสต์กับ Postgres จริงทุก PR

**คำตอบของฉัน**

&nbsp;

## 2. Idempotency คืออะไร และทำให้ pipeline นี้ idempotent ได้ยังไง

**ประเด็น**
- รันซ้ำกี่ครั้งก็ได้ผลเหมือนรันครั้งเดียว
- ใช้ `line_id` เป็น primary key แล้วทำ `INSERT ... ON CONFLICT` → รอบสองได้ insert 0 แถว
- ไฟล์รายวันแทนที่ข้อมูลทั้งวัน ฝั่ง dbt ใช้ `delete+insert` ตาม `date_key`
- หลักฐาน: ลบไป 10,098 แถวแล้วรันใหม่ ได้กลับมาครบ และทดสอบให้ Airflow ล้มกลางทางแล้ว clear ข้อมูลไม่ซ้ำ (วัน 2011-01-05 ยังเป็น 1,117 แถว)

**คำตอบของฉัน**

&nbsp;

## 3. Grain ของ fact table คืออะไร และรู้ได้ยังไง

**ประเด็น**
- grain = 1 บรรทัดใน invoice ที่มีลูกค้า
- เช็กก่อนว่า invoice_no + stock_code ไม่ unique: ซ้ำ 9,694 คู่ ใน invoice เดียวซ้ำได้ถึง 20 ครั้ง
- จึงสร้าง `line_id` = invoice_no + ลำดับบรรทัด
- ข้อจำกัด: `line_id` ขึ้นกับลำดับแถวในไฟล์ต้นทาง

**คำตอบของฉัน**

&nbsp;

## 4. ทำไมต้องใช้ transaction ถ้าโหลดล้มกลางทางจะเกิดอะไรขึ้น

**ประเด็น**
- COPY เข้า temp table, upsert และลบแถวของวันที่ไม่อยู่ในไฟล์ อยู่ใน transaction เดียว
- ถ้าล้ม rollback ทั้งหมด จะไม่มีข้อมูลค้างครึ่ง ๆ กลาง ๆ
- audit row แยกไว้คนละ transaction เพื่อให้ยังบันทึกได้ว่ารอบนั้นล้ม
- มีเทสต์ `test_failed_run_rolls_back_and_is_audited` ครอบไว้

**คำตอบของฉัน**

&nbsp;

## 5. จัดการข้อมูลเสียยังไง ทำไมไม่ทิ้งแถวที่ไม่มี CustomerID

**ประเด็น**
- 4 กฎ: ราคา ≤ 0, invoice C ที่ quantity เป็นบวก, วันที่ว่าง, line_id ซ้ำ → ปฏิเสธ 2,517 แถว (0.46%)
- circuit breaker ตัดทั้ง batch ถ้าแถวเสียเกิน 5% เพราะน่าจะเป็นไฟล์ export ที่พัง
- แถวที่ไม่มี CustomerID มี 24.9% ซึ่งเป็นการขายจริงแบบ guest (15% ของรายได้) ไม่ใช่ข้อมูลเสีย และถ้าเป็นกฎ breaker จะตัดทุก batch
- มี 2 วันจริงที่เกิน 5% → ให้คนตรวจแล้ว override ได้ และค่าที่อนุมัติถูกบันทึกใน audit

**คำตอบของฉัน**

&nbsp;

## 6. Incremental loading ทำงานยังไง ถ้ามีข้อมูลมาช้าหรือมีวันหายจะเกิดอะไรขึ้น

**ประเด็น**
- `load --date` โหลดทีละวัน วันที่ไม่มีไฟล์บันทึกเป็น skipped และไม่ error
- `--since-last` เริ่มจาก watermark (วันล่าสุดที่มีข้อมูลจริง) และโหลดวันนั้นซ้ำ เผื่อข้อมูลมาไม่ครบ
- บั๊กที่เจอ: โหลดข้ามวันแล้ว watermark กระโดด 22 วันหายไป (32,781 แถว) → แก้โดยเริ่มจากวันแรกที่ยังขาด
- หลักฐาน: ลบ 3 วันท้ายแล้วรัน `--since-last` ข้อมูลตามทันเอง

**คำตอบของฉัน**

## 7. Backfill ใน Airflow ทำยังไง ถ้า task ล้มกลางทางทำยังไง

**ประเด็น**
- `catchup=True`, `retries=2`, `max_active_runs=1` แต่ละ run ประมวลผลข้อมูลของวัน `{{ ds }}`
- backfill มกราคม 2011 ผ่าน 31/31 run
- Airflow 3: backfill รันเฉพาะตอน DAG unpause และ `@daily` ใช้ timetable แบบใหม่ จึงเปลี่ยนไปใช้ `CronDataIntervalTimetable`
- ทุก task เป็น idempotent จึง retry หรือ clear ได้โดยไม่ต้องกลัวข้อมูลซ้ำ

**คำตอบของฉัน**

## 8. ทำไมใช้ dbt และตรวจได้ยังไงว่าตัวเลขถูก

**ประเด็น**
- SQL แยกเป็น model มี lineage ชัด มี tests ในตัว และ incremental ได้
- 24 tests: unique, not_null, relationships, accepted_values และ test เทียบ fact กับ staging รายวัน
- reconciliation กับตารางเดิม: รายได้ตรงกันที่ 8,300,065.81 ส่วนจำนวนแถวที่ต่างกัน 40 แถวคือแถวราคา 0 ที่ validate ปฏิเสธ

## 9. ให้สิทธิ์ BI เข้าถึงข้อมูลยังไง

**ประเด็น**
- role `metabase_ro`: SELECT ได้เฉพาะ `marts` ห้ามเข้า raw, audit, staging และห้ามเขียน
- `ALTER DEFAULT PRIVILEGES` เพราะ dbt สร้างตารางใหม่ทุกครั้งที่ build
- 1 role ต่อ 1 ระบบที่ใช้ เรียนรู้จากตอนที่ชื่อ `analyst_ro` ชนกับ agent อีกตัว
- เทสต์และ CI ยืนยันว่าอ่าน raw ไม่ได้ และลบข้อมูลไม่ได้

## 10. ปัญหาที่ยากที่สุดคืออะไร และถ้าข้อมูลใหญ่ขึ้น 100 เท่าจะเปลี่ยนอะไร

**ประเด็น (เลือกปัญหามา 1 เรื่องแล้วเล่าแบบ STAR)**
- watermark ข้าม 22 วัน → เจอได้เพราะเทียบจำนวนแถวกับตอนโหลดทั้งไฟล์ → แก้ด้วยการเช็กวันที่ขาด → ตัวเลขกลับมาตรงทุกหลัก
- หรือเรื่อง override ที่อนุมัติแล้วไม่ถูกจำ จน pipeline ค้างอยู่วันเดิม

**ถ้าใหญ่ขึ้น 100 เท่า**
- partition `raw` และ `fact_sales` ตามวัน
- landing อยู่บน S3 แล้ว (Phase 8) จึงย้ายไป AWS ได้ทันที ใช้ warehouse ที่ scale ได้ (BigQuery, Snowflake) หรือ query Parquet ตรง ๆ ด้วย DuckDB, Athena หรือ Spark
- รัน validate แบบ streaming หรือแบ่ง chunk
- dims เป็น incremental หรือ SCD แทนการ rebuild ทั้งหมด
- แจ้งเตือนจาก notify ไป Slack หรือ email

**คำตอบของฉัน**

## 11. ทำไม landing เป็น Parquet บน S3 และ data lake ต่างจาก warehouse ยังไง

**ประเด็น**
- Parquet เป็น columnar: เก็บข้อมูลทีละคอลัมน์ บีบอัดได้ดีและเก็บชนิดข้อมูลไว้ด้วย 305 ไฟล์ขนาด 11 MB เทียบกับ CSV ที่ 46 MB ถ้าอ่านแค่ 2 คอลัมน์ก็ไม่ต้องอ่านทั้งไฟล์
- partition `date=YYYY-MM-DD/`: โหลดหรือโหลดซ้ำทีละวันได้โดยไม่ต้องสแกนทั้งหมด และเป็นรูปแบบ Hive ที่ Spark, Athena และ DuckDB อ่านได้เลย
- lake เก็บไฟล์ดิบราคาถูก จะ replay ใหม่เมื่อไหร่ก็ได้ ส่วน warehouse (Postgres) เก็บตารางที่ผ่าน validate แล้ว มี type ครบและพร้อม query
- medallion: landing คือ bronze, raw และ staging คือ silver, marts คือ gold
- อ่านผ่าน fsspec และ S3 API จึงใช้โค้ดชุดเดียวกันได้ทั้งในเครื่อง, RustFS และ AWS
- หลักฐาน: โหลดใหม่ครบ 305 วันจาก S3 ได้ insert 0 และ update 0
- เรื่องที่เจอ: image ของ MinIO ไม่มีให้ดึงแล้ว จึงเปลี่ยนไปใช้ RustFS ที่เป็น S3-compatible เหมือนกัน และ Parquet ช่วยให้เจอคอลัมน์ Description ที่มีชนิดข้อมูลปนกัน ซึ่ง CSV ซ่อนไว้

**คำตอบของฉัน**
